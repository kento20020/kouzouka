# 08 鍛え方

この力は、本を読むだけでは身につきません。**図を描く → 実際に試す → ズレを見つける**の繰り返しで鍛えます。

## 1. 既存アプリを逆から設計する（一番効く）

毎日使うアプリの画面遷移図を描きます。そのうえで、機内モード、戻るの連打、送信直後の強制終了、通知からの起動を実際に試し、「なぜこう作ったのか」を推測します。
**良いアプリほど異常系が丁寧に作られています。**

### 手順

1. **対象を選ぶ**：毎日使っていて、通信と入力があるアプリ（チャット・SNS・ショッピング・銀行・AIアプリ）
2. **L3 画面遷移図を描く**（30分）：主要な画面10個前後と、そのつながり。各遷移が push／replace／reset のどれかを、戻るボタンを押して確かめる
3. **1機能を選んで L4 状態遷移図を描く**（30分）：投稿する・送金する・質問するなど
4. **状態×イベント表を作る**：行に状態、列に下の「試すことリスト」を並べる
5. **実際に試して表を埋める**：予想と実際の挙動を両方書く
6. **「なぜこう作ったのか」を推測する**：予想と違ったマスについて、作り手の意図を考える

### 試すことリスト

| 試すこと | やり方 | 見るところ |
| --- | --- | --- |
| 機内モード | 送信直前・送信直後・読み込み中にオンにする | エラーの出し方、入力が残るか、復帰後に自動で再送するか |
| 戻るの連打 | 画面が切り替わる最中に戻るを何度も押す | 2画面戻るか、画面が崩れるか |
| ボタンの連打 | 送信・購入・いいねを素早く何度も押す | 二重に投稿・購入されないか |
| 送信直後の強制終了 | 送信を押した直後にアプリを終了し、もう一度開く | 送信されたのか、されていないのか、画面で分かるか |
| 通知からの起動 | アプリを終了した状態で通知をタップする | どの画面が開くか、戻るとどこへ行くか |
| 放置 | 入力画面を開いたまま一晩放置してから送信する | セッション切れの扱い、入力が残るか |
| 遅い回線 | 下の「回線を遅くする方法」を使う | 読み込み中の表示、タイムアウトまでの時間 |
| 画面回転・文字サイズ最大 | 入力途中で回転する、端末の文字サイズを最大にする | 入力が消えないか、レイアウトが崩れないか |
| 2台で同時に操作 | スマホとPCで同じアカウントにログインし、同時に操作する | 片方の変更がもう片方にいつ反映されるか |

### 端末で異常を起こす方法

| やりたいこと | Android | iOS | Web（Chrome） |
| --- | --- | --- | --- |
| 回線を遅くする | エミュレータの設定でネットワーク速度・遅延を変える | 開発者向け設定の「Network Link Conditioner」（Xcode を使って開発者モードを有効にした端末） | DevTools の Network タブで「Slow 4G」などを選ぶ |
| オフラインにする | 機内モード | 機内モード | DevTools の Network タブで「Offline」 |
| 画面の破棄・プロセス終了を再現 | 開発者向けオプションの「アクティビティを保持しない」をオン | ― | ― |
| アプリを裏へ回して戻す | ホームボタン・最近使ったアプリ | ホーム画面に戻る | 別のタブに切り替える |
| 通信の中身を見る | Android Studio の Network Inspector | Xcode の Instruments（ネットワーク）、プロキシツール | DevTools の Network タブ |

「アクティビティを保持しない」をオンにすると、画面を離れるたびに画面が破棄されます。戻ってきたときに入力やスクロール位置が消えるアプリは、状態の保存ができていません。

## 2. 今の仕事をスイムレーン図で描く

運用保守の障害対応やリリース手順は「今のやり方」の材料が豊富です。例外や属人化がそのまま見えるので、中小企業でのヒアリングの予行演習にもなります。

### 描くと効く業務の例

| 業務 | 見えてくるもの |
| --- | --- |
| 障害対応（検知 → 連絡 → 調査 → 復旧 → 報告） | 夜間・休日の連絡経路、判断できる人が1人しかいない場所 |
| リリース手順 | 手作業の確認、承認待ち、失敗したときの戻し方（切り戻し）が書かれていない場所 |
| 問い合わせ対応 | 1次対応から2次対応への引き継ぎで情報が落ちる場所 |
| 月次の作業 | 月末だけ発生する例外、Excel の手作業 |

### 描いた後にやること

1. 図を同僚に見せて「実際はこうなっていない？」を聞く（ここで出てくる例外が本物）
2. 図の各箱に8つの問い（[06章](06-eight-questions.md)）を当てる
3. 「待ち」「手作業」「1人しかできない」に印をつけ、改善案（To-Be）を描く

## 3. 個人開発で、実装前に L2〜L4 を書く

Mermaid（`stateDiagram`・`sequenceDiagram`）はテキストなので Git で管理できます。GitHub は Markdown の中の Mermaid をそのまま図として表示します。

### 進め方

1. ユースケース記述（[テンプレート](../templates/usecase.md)）を1つ書く
2. 状態遷移図を Mermaid で描く
3. 状態×イベント表（[テンプレート](../templates/state-event-table.md)）を全マス埋める
4. AI にレビューさせる（[プロンプト](../templates/ai-review-prompt.md)）
5. 表をコードの型にする（[サンプル](../examples/send-to-ai/sendState.ts)のように、全マスを書かないと型エラーになる形にする）
6. 表からテストを作る

AIに「この状態×イベント表の空欄と矛盾を指摘して」とレビューさせるのも簡単です。
ただし、AI の指摘は「候補」として扱い、採用するかどうかは自分で判断します。

## 4. テスト技法を学ぶ

状態遷移テスト・デシジョンテーブル・境界値分析。**JSTQB Foundation Level の範囲がちょうど良いです。**
シラバス（試験範囲の資料）は JSTQB のサイトで無料公開されています。資格を取らなくても、シラバスを読むだけで「テスト技法の地図」が手に入ります。

| 技法 | 何に使うか | この教材とのつながり |
| --- | --- | --- |
| 状態遷移テスト | 状態×イベントの全マス・全遷移を試す | Step5 の表がそのままテストケースになる |
| デシジョンテーブル | 条件の組み合わせの漏れをなくす | 「会員かつクーポンありかつ初回」のような分岐 |
| 境界値分析 | 上限・下限のちょうどと1つ外を試す | 入力の文字数、ページ分け、利用回数の上限 |
| 同値分割 | 同じ扱いになる入力をまとめて、代表だけ試す | 入力系の観点 |
| ユースケーステスト | 基本・代替・例外フローを1本ずつ試す | Step2 のユースケース記述 |

## 5. 4週間プラン

| 週 | やること | 成果物 | 自己チェック |
| --- | --- | --- | --- |
| 1 | アプリ2つを逆から設計（L3〜L4） | 画面遷移図2枚、状態×イベント表2枚、「なぜこう作ったか」のメモ | 試すことリストを全部試したか。予想と違ったマスが3つ以上見つかったか |
| 2 | 職場の業務1つを L1〜L2 で描く | スイムレーン図1枚、ユースケース記述2本 | 同僚に見せて、自分が知らなかった例外が1つ以上出てきたか |
| 3 | 自分のアプリの1機能を L2〜L5 まで | ユースケース、状態遷移図、状態×イベント表、シーケンス図 | 表に空欄がないか。一方向ドアのマスにシーケンス図があるか |
| 4 | 状態遷移テストを学び、3週目の表をテストケースにする | テストケース一覧（できれば自動テスト） | 全マス（無視するマスも含む）がテストになっているか |

## 6. もっと続けるなら（5〜8週目）

| 週 | やること | 成果物 |
| --- | --- | --- |
| 5 | 3週目の表をコードの型にする（全マスを書かないと型エラーになる形） | 状態機械のコードとテスト |
| 6 | サーバー側に冪等キーを入れ、「返る途中で切断」を再現して確かめる | 冪等キーの実装、再現手順 |
| 7 | 優先度シートで Tier を分け、既知の挙動を書く | 優先度シート、既知の挙動リスト |
| 8 | 誰かの業務を（友人・家族の仕事でもよい）ヒアリングして L0〜L2 を描く | ヒアリングシート、目的文、スイムレーン図、ユースケース一覧 |

8週目は、中小企業でのヒアリングの本番に近い練習です。ヒアリングシート（[テンプレート](../templates/hearing-sheet.md)）を使い、「実物を見せてもらう」まで含めてやってみてください。
